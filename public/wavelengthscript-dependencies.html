# Working dependency audit: 0.1.0–0.15.0

Scope: all fifteen retained repository-local `wls.collections` releases,
their actual WavelengthScript algorithms, package/locked execution,
developer tooling, distribution and browser learning examples.
No 0.16.0 package or unrelated expansion is included.

## What is implemented

These are working bounded native libraries, not encoded descriptions or
placeholder package names. Every declared operation executes WavelengthScript
instructions and returns an observable value or an explicit execution error.
The retained string-list profile and the separate Map/string-Set profile
remain distinct; selecting a later version does not silently mix profiles.

The compiler, interpreter and CLI are still TypeScript/JavaScript host software.
The dependency implementations do not yet replace the project's entire host
runtime, browser, database, networking or AI dependencies. These are local
packages, not packages already published to a public registry.

See [the complete inventory](wavelengthscript-dependencies.md) and each linked
release guide for exact APIs, input representations and resource limits.

## Findings and remediation

1. **Usability gap:** the browser workspace offered release examples only
   through 0.9.0, leaving 0.10.0–0.15.0 functions undiscoverable there.
   The workspace now loads real canonical source, inputs and expected results
   for those releases. Actual browser-component tests select, execute and
   assert independently specified output values for every added release.
2. **Disclosure gap:** dependency documentation existed in repository Markdown
   but had no accessible complete public guide linked from the workspace.
   `/wavelengthscript-dependencies.html` now contains the full guide index,
   release documents, implementation boundaries and audit. It is generated
   from the same Markdown files used for GitHub disclosure, not separately
   maintained promotional text. A consistency check rejects stale output.
3. **Audit evidence gap:** earlier coverage did not consolidate independently
   expected successful outputs for every operation across every retained
   version's package and locked-package entry points. The new cross-release
   suite asserts complete successful-operation coverage, actual RETURN traces,
   expected failure classes and unchanged deeply frozen inputs. It adds explicit
   add/remove/indexed-recipient cases where the smoke fixtures lacked successful
   examples. Expected values are fixture data, never generated by the VM.
4. **Execution-boundary fault:** the legacy contract/preview compiler rejected
   list-profile source but did not similarly reject Map-profile source. Map/Set
   instruction lines could therefore fall through to logging-only legacy
   instructions, a misleading substitute for real native execution.
   The shared boundary guard now rejects `WLS-MAP` headers and native `MAP_`
   instructions before legacy compilation. Every canonical Map/Set program is
   tested against both the legacy and Python compilers, including header-stripped
   Map source; ordinary quoted strings and comments remain permitted.

No canonical `.wls` source bytes, retained lock fingerprints, VM permissions or
execution budgets were changed by these fixes. No implementation fault in those
algorithms was reproduced by the added cross-release expected-result checks.
This statement is limited to the tests performed, not proof of no possible bugs.

**Additional export correction:** the immutable-tree import checker treated
`.generated` in a TypeScript basename as an unsupported loader extension.
It now resolves only concrete `.generated.ts` or `.generated.tsx` regular blobs
included in the proposed Git tree. Missing targets and unsupported loaders still
fail. This is direct-file metadata validation, not a full Node/TypeScript
resolver or a source-authentication guarantee.

    → spectral-coordinate labels

## Concrete implementation example and limits

One existing character-table profile has 128 entries:

```text
λ(i) = 380 + 3.125 × i nm,  i = 0…127
A: ASCII 65 → 583.125 nm
B: ASCII 66 → 586.250 nm
```

The table spans 380 through 776.875 nm. A 380–780 nm design interval does
not mean its final indexed entry equals 780 nm.

The legacy modulo projection uses `character code % 128`. It can alias inputs:
`A` (65) and `Á` (193) project to the same entry. It is not lossless
arbitrary-Unicode transport. Retain the original payload and use an agreed
lossless transport when full text must be recoverable.

These numerical assignments do not show that a laser emitted those wavelengths,
that a detector decoded them, or that a device executed the associated operation.
Calculating frequency or photon energy from a wavelength does not establish a
new physical law or a physically compressed character.

The project also uses different account-derivation, VM-name-fingerprint and
proposed optical-bin profiles. They are not interchangeable. Name averaging is
lossy; finite spectral addresses can collide; labels are not authentication.

implementation in the revision being evaluated. Development and GitHub branches

# Internal dependency audit: 0.1.0–0.11.0

Date: 31 October 2026. Scope: the eleven repository-local `wls.collections`
releases, both bounded execution profiles, all 54 canonical programs,
manifests, source locks, test tooling, CLI isolation and portable distribution.
This is an internal engineering audit, not independent security certification.

## Findings and fixes

### 1. List interpreter could invoke input getters

**Severity: medium; direct JavaScript API boundary.**

The original list interpreter enumerated input values with `Object.entries`
and repeatedly read array elements while validating them. Ordinary property
getters could therefore run during input validation, or change their return
values between validation and snapshotting. JSON-only CLI inputs cannot
contain these accessors, but the exported JavaScript API also needed protection.

**Fixed:** require plain/null-prototype input records; inspect own data
descriptors without reading accessors; reject symbol register names, sparse
arrays, array accessors, extra array properties and array subclasses. Read
each accepted element once into an independent snapshot. Supported frozen
arrays and null-prototype records remain usable.

This matches the existing Map profile's data-boundary approach. It is not
a sandbox against arbitrary JavaScript supplied by a hostile host: proxies
can run reflection traps, and a compromised interpreter/host remains outside
the guarantee. Untrusted external data should enter through a serialized-data
boundary, not executable JavaScript objects.

### 2. Earlier library shortcuts skipped required operands

**Severity: medium; malformed-input correctness.**

Examples included `recipient.remove` accepting a non-string or missing query
on an empty list, and `map.intersection`, `map.difference`,
`set.intersection` and `set.difference` skipping right-operand checks when
the left input was empty. A skipped branch must not make an invalid API
argument valid.

**Fixed:** an exhaustive canonical-library input contract is checked against
the interpreter's safe input snapshot before execution. Every required list,
Map, string and integer argument is checked even when the algorithm would
otherwise return early. Missing registers fail explicitly.

Contracts bind to exact canonical source bytes. Identical-source aliases
must have identical contracts. Custom edited programs retain the generic
profile's opcode/type rules and must implement their own argument checks;
they do not inherit a standard-library API merely by resembling its source.

4. **Compile** shows every compiled instruction, resolved branch operands,
   original source line and coordinate-derived wavelength metadata.
5. **Execute** or **Run all** validates and recompiles the current source,
   runs the bounded interpreter and shows the returned JSON value and **only
   actually visited instructions**. Repeated loop visits remain visible.
   Compiled instructions are not accepted back as executable input.

Source, input, example or profile changes clear stale compilation and results.
Compilation/runtime/input errors are explicit and never display a prior result
as a fresh success. Failed executions do not claim a successful trace. Profile
switches reset the workspace; there is no implicit persistence or filesystem.
JSON text is separately limited to 16,384 characters before parsing; all VM
value and resource limits below still apply after parsing.

The selector and required header are separate checks: unknown versions,
missing headers and foreign-profile source are rejected by the collection
compiler. Collection source and recognizable headerless `LIST_*` instructions
are rejected before other-language preview translation and by the browser and
server contract compilers, rather than silently going through generic `EXEC`.
Python parsing and its `WLS-PY/1` instruction format remain unchanged.

### Instruction interface

Each instruction is an uppercase operation followed by a JSON argument array.
Register and label names start with an ASCII letter and contain at most 32
letters, digits or underscores. Define a label on its own line as `:scan`.
Blank lines and whole-line `//` comments are ignored after the required header.

| Instruction | Arguments | Behaviour |
| --- | --- | --- |
| `LIST_NEW` | `["dest"]` | Empty string list |
| `LIST_COPY` | `["dest","items"]` | Independent list copy |
| `LIST_LEN` | `["dest","items"]` | List length |
| `LIST_AT` | `["dest","items","index"]` | Checked zero-based retrieval |
| `LIST_PUSH` | `["items","value"]` | Bounded string append |
| `CONST` | `["dest", literal]` | String, safe integer or boolean literal |
| `EQ` | `["dest","left","right"]` | Exact scalar comparison |
| `LT` | `["dest","left","right"]` | Safe-integer comparison |
| `INC` | `["integer"]` | Checked integer increment |
| `JTRUE` | `["condition","label"]` | Branch on a boolean |
| `JUMP` | `["label"]` | Unconditional branch |
| `RETURN` | `["value"]` | Return a scalar or copied string list |

Example of an independently editable program:

```text
WLS-COLLECTION/1
LIST_LEN ["size","items"]
RETURN ["size"]
```

This is an explicitly versioned, capability-free instruction profile, not a
general module/import system. Source reuse currently means loading or copying
these bounded source programs and supplying named input registers.

## Bounds and failure behaviour

- Source: 8,192 characters; at most 128 instructions.

- Lists: at most 20 strings; each string at most 256 UTF-16 code units.

  explicitly. Infinite loops exhaust the cycle budget.
- Programs and argument arrays are frozen after compilation. The public runner
  recompiles source instead of accepting caller-forged instruction records.
- Input/output lists are copied; errors do not mutate the selected list.

- No network, DOM, file, database, wallet or financial capabilities exist in

## Separate execution and release contracts

`WLS-COLLECTION/1` has not gained map values or instructions. Its old sources,
limits, string-list behavior and APIs remain unchanged.

The 0.3.0 map-only surface is intentional: it selects a different value and

is rejected. No ranges, downloads, transitive dependencies or profile
translation are supported.

`COLLECTION_LIBRARY_RELEASE` and `COLLECTION_LIBRARY_LATEST_RELEASE` retain
their 0.1.0 and 0.2.0 identities for existing consumers. `MAP_LIBRARY_RELEASE`
identifies 0.3.0. `COLLECTION_PROGRAM_IDS` still lists the nine collection IDs;
`MAP_PROGRAM_IDS` lists the eight map IDs and `LIBRARY_PROGRAM_IDS` lists both.

## Values, equality, order and errors

Maps cross the JSON boundary as ordered entries, not arbitrary object fields:

```json
{ "entries": [["name", "Ψ🙂"], ["__proto__", "ordinary text"]] }
```

- Keys and values must be strings. No nested maps, lists, objects, null or
  numeric coercion. Scalars available to programs are strings, booleans and
  safe integers.
- Key equality is exact JavaScript string equality (UTF-16 code units).
  No trimming, case folding, normalization or locale comparison occurs.
  `é` and `e\u0301` are different keys; empty strings, control characters,
  astral characters and lone surrogate code units are data. Limits count
  UTF-16 code units, so `🙂` counts as two. Files themselves require valid
  UTF-8 in the CLI; JSON escapes may represent lone surrogate code units.
- Incoming duplicate keys are **rejected**, never silently collapsed.
- Input entry order is insertion order, including numeric-looking keys.
  Setting a new key appends it. Overwriting an existing key replaces its
  value without moving it and is allowed at capacity. Delete preserves the
  order of surviving entries; delete then reinsert appends the key.
- Missing `get` throws `CollectionVMError("Map key is missing.")`.
  `has` returns false. Delete of an absent key returns a fresh unchanged map.
  Out-of-range indexes throw; no `undefined`, null or magic sentinel result.
- Every input map is validated and snapshotted. Every returned map, entry
  array and pair is frozen. Get has no side effects; copy/set/delete produce
  new maps without changing input or other registers, even when the destination
  register aliases an operand. Failure does not partially change caller data.
- Keys such as `__proto__`, `constructor` and `toString` are plain entry
  strings, never property lookups. Sparse arrays, malformed pairs, extra
  properties, accessors, inherited map data and cyclic/nested values fail.
  The boundary is JSON/data values, not sandboxing hostile JavaScript proxies
  or caller-defined platform built-ins.

## Fixed catalogue and instruction signatures

Each `.wls` file is canonical; the generated portable artifact contains its
verbatim source. Operations execute inside the separate interpreter; typed
bridges in `shared/wls-map-library.ts` only marshal inputs/results.

| Program ID | Inputs | Result |
|---|---|---|
| `map.empty` | none | empty map |
| `map.copy` | `map` | fresh map |
| `map.size` | `map` | entry count |
| `map.has` | `map`, `key` | boolean |
| `map.get` | `map`, `key` | string, or missing-key error |
| `map.set` | `map`, `key`, `value` | new map |
| `map.delete` | `map`, `key` | new map |
| `map.keyAt` | `map`, `index` | key at zero-based insertion position |

MAP_NEW [destination]

MAP_GET [destination, map, key]

integer `LT [destination,left,right]`, checked `INC [register]`,
boolean `JTRUE [condition,label]`, `JUMP [label]`, `:label`, comments and
`RETURN [register]` are supported. A program must end in RETURN. Unknown
instructions, malformed operands, invalid labels, undefined registers and
type mismatches fail explicitly. Map equality is not a scalar operation.

| Entries per map | 20 |
| Key / value length | 256 UTF-16 code units each |
| Source length | 8,192 code units |
| Instructions | 128 |
| Executed instructions (cycles) | 1,024, including RETURN |
| Live registers, including inputs | 32 |
| Charged live register memory | 65,536 logical bytes |

Logical memory is deterministic, not an assertion about the JavaScript
engine's actual heap: scalar number/boolean = 16; string = 16 + 2 × length;
map = 32 + sum(32 + 2 × (key length + value length)) over entries. Each
register is charged independently, even for shared immutable values.
Replacing a register releases its previous charge before charging the
replacement. Over-limit input or instruction results fail before register
commit. Source, instruction/label tables and traces have separate fixed
limits above; each operation scans/copies at most 20 pairs. Snapshot/return
and instruction temporaries are individually bounded by one maximum map,
not included in the live-register charge. This is finite interpreter work,
not a wall-clock timeout or host-process memory isolation.

# Exact-source integrity locks for local WavelengthScript dependencies

Locks also cover the separate [map-only 0.3.0 release](wavelengthscript-maps-v0-3.md)
and [map composition 0.4.0](wavelengthscript-map-composition-v0-4.md),
plus [Map + string-key Sets 0.5.0](wavelengthscript-sets-v0-5.md),
and [Map values/Set comparisons 0.6.0](wavelengthscript-map-set-v0-6.md),
and [Map entries/Set symmetric difference 0.7.0](wavelengthscript-map-set-v0-7.md),
and [conditional Maps 0.8.0](wavelengthscript-map-set-v0-8.md)
and [ordered selection 0.9.0](wavelengthscript-map-set-v0-9.md),
and [Map value queries 0.10.0](wavelengthscript-map-set-v0-10.md),
and [Map value transformations 0.11.0](wavelengthscript-map-set-v0-11.md),
and [ordered Map value operations 0.12.0](wavelengthscript-map-set-v0-12.md),
and [indexed Map reads 0.13.0](wavelengthscript-map-set-v0-13.md),
and [ordered membership queries 0.14.0](wavelengthscript-map-set-v0-14.md),
and [ordered Map/Set slices 0.15.0](wavelengthscript-map-set-v0-15.md),
with `WLS-MAP/1` source. Retained 0.1.0/0.2.0 collection locks stay valid
without regeneration; switching execution profiles or dependency versions
requires an explicit reviewed new lock.

`WLS-LOCK/1` adds SHA-256 commitments to the existing offline dependency
manifests. It detects changes to the exact manifest text and each declared
packaged program source, including whitespace changes under the same version.

This is an integrity comparison against a lock you trust. It is **not** a digital
signature, author authentication, full runtime verification or a privacy claim.

## Create, verify and execute

First check that the packaged library matches the canonical `.wls` files:

```sh
npm run check:wls-library
```

Create a new lock explicitly, after reviewing the manifest and its sources:

```sh
node_modules/.bin/tsx scripts/wls-collections-cli.ts package-lock scripts/fixtures/wls-collection-package.json > collection.lock.json
```

The command emits JSON to stdout; it does not select or overwrite a lockfile
itself. The shell's `>` will overwrite an existing destination: choose a new
file or preserve your reviewed lock before deliberately replacing it.

```sh
node_modules/.bin/tsx scripts/wls-collections-cli.ts package-verify scripts/fixtures/wls-collection-package.json collection.lock.json
node_modules/.bin/tsx scripts/wls-collections-cli.ts package-run-locked scripts/fixtures/wls-collection-package.json collection.lock.json string.contains scripts/fixtures/wls-package-inputs.json
```

The example returns `value: true` and `integrity: "verified"`. Add `--trace`
after the input file to inspect visited instructions. Verification failures
exit with code `1`, without executing the program or regenerating the lock.
The manifest, lock and input files are not modified.

## Test a suite against a locked package

Select the locked test workflow explicitly:

```sh
node_modules/.bin/tsx scripts/wls-collections-cli.ts package-test-locked scripts/fixtures/wls-collection-package.json collection.lock.json scripts/fixtures/wls-package-tests.json
```

The arguments are the manifest, trusted lock and existing `WLS-TEST/1` JSON
suite, in that order. Every case must use a fixed catalogue program ID declared
by the manifest. Case program references cannot be source paths or URLs.
No `--trace`, relocking option or additional suite fields are accepted.

The entire suite is validated, all declared sources are captured, compiled
and verified against the lock (including programs unused by the suite), and
every case is bound to a declared source before any case executes. All cases
use that one verified snapshot; there is no reloading between verification
and cases or per-case re-verification. Invalid sources, missing declarations
and integrity failures cannot satisfy an expected runtime-error assertion.

Success emits the ordinary `WLS-TEST/1` report with `integrity: "verified"` and
exits `0`. Assertion failures emit the report with failure reasons and exit `1`.
Malformed/unreadable inputs, unsupported declarations and integrity mismatches
exit `1` with a diagnostic on stderr and no partial report or executed cases.
Reports do not include input values, actual values, sources or raw runtime
diagnostics. The command does not modify the manifest, lock or suite.

Existing limits remain: 64 cases, 131,072 UTF-16 code units of suite text,
16,384 per-case input JSON code units, the existing name/expectation limits,
and the VM's source, value, instruction and cycle bounds. CLI reads remain
bounded regular-file reads with strict UTF-8. This command starts no application,
database or network service and grants no new VM capabilities.

## What is bound

The strict lock contains:

- `profile`: exactly `WLS-LOCK/1`.
- `manifestSha256`: SHA-256 of the exact manifest text encoded as UTF-8.
- `package`: consumer name, version and execution profile.
- `dependencies`: the resolved exact-version local dependency identity.
- `programs`: the declared IDs in manifest order, each with its exact packaged
  source's UTF-8 SHA-256 digest.

Hash strings are exactly 64 lowercase hexadecimal characters. Unknown fields,
missing/extra/duplicate/reordered program entries, unsupported IDs and malformed
identity/hash fields fail. JSON whitespace and property ordering in the lock
itself may change; the manifest and source commitments remain exact.

Limits are unchanged for manifests, source and program execution. Lock text is
limited to 16,384 UTF-16 code units, with strict UTF-8 and bounded regular-file
reads at the CLI. SHA-256 must be available through Web Crypto; there is no
weaker fallback. Malformed Unicode source cannot be silently replaced while
hashing.

## Safe execution sequence

All sources are captured and compiled before the first asynchronous hash
operation. Locked execution uses the **same captured source** that was verified,
not a later library lookup. Every declared source must match, not only the
selected program.

The CLI finishes integrity and declaration checks before reading the selected
input file. Runtime inputs are then checked by the existing VM immediately
before execution. No externally forged resolved plan or bytecode is accepted.

`shared/wls-package-lock.ts` exports asynchronous creation, verification,
verified-source loading and locked-execution APIs. These are TypeScript/Web
Crypto bootstrap tools for Node/browser bundlers; portable distribution
bundles do not automatically acquire these exports.

## Boundaries that remain

- Creating a lock does not decide whether its sources are safe or reviewed.
- Someone who can replace both a lock and its sources can create matching
  malicious content. Protect/review the expected lock independently.
- Only the manifest and declared program sources are committed. The
  interpreter, host JavaScript, compiler, tooling dependencies and browser
  delivery are not covered by these digests.
- Undeclared catalogue programs and canonical on-disk `.wls` files outside the
  packaged source snapshot are not hashed.
- `package-run`, ordinary `run` and the current `test` command remain
  **unlocked** workflows. Select `package-run-locked` or `package-test-locked`
  explicitly for integrity-checked execution.
- There is no registry, download, installer, install hook, signature custody,
  general transitive dependency solver, live-service change or activation of
  operator-inaccessible privacy.

See [dependency manifests](wavelengthscript-package-manifests.md) and
[local tools](wavelengthscript-local-tools.md).

## Verification

`server/wls-package-lock.test.ts` checks independent Node SHA-256 agreement,
determinism, metadata/hash/source changes, strict schemas, crypto unavailability
and source changes during asynchronous hashing. The CLI tests exercise
creation/verification/locked execution in separate processes, failure status,
unchanged locks and refusal before input-file reading.

`server/wls-package-test-locked.test.ts` and
`scripts/wls-package-test-locked-cli.test.ts` cover locked suites, validation
before any execution, unused declared source verification, snapshot reuse
across asynchronous hashing and multiple cases, unchanged limits, safe
reports and real CLI success/failure statuses.

# Repeatable tests for WavelengthScript libraries

WavelengthScript programs can now be tested using a local JSON suite rather
than writing a separate TypeScript/Vitest harness for each program consumer.
This is host-backed developer tooling for the **existing** language and packaged
libraries, not a new language grammar or a self-hosted test runner.

## Run the included example

```sh
npm run check:wls-library
node_modules/.bin/tsx scripts/wls-collections-cli.ts test scripts/fixtures/wls-library-smoke.json
```

The example exercises exact search, first matching index, concatenation and an
expected out-of-range error. A passing suite exits with code `0`; assertion
failures or an invalid suite exit with code `1`. Assertion failures produce a
JSON report on stdout; invalid suites produce a bounded error on stderr.
No application, database, wallet or network service is started.

## Write a suite

```json
{
  "profile": "WLS-TEST/1",
  "cases": [
    {
      "name": "Find an exact match",
      "program": "string.contains",
      "inputs": {"items":["alpha","beta"],"value":"beta"},
      "expect": {"value":true}
    },
    {
      "name": "Reject an invalid index",
      "program": "recipient.at",
      "inputs": {"items":[],"index":0},
      "expect": {"error":true}
    }
  ]
}
```

Use exactly the documented keys. Each case has a unique nonblank name and a
program ID from `COLLECTION_PROGRAM_IDS` or the separate `MAP_PROGRAM_IDS`,
plus its named JSON input registers.
`expect` contains **either** `value` or `error: true`, not both.

Expected values are strings, safe integers, booleans, bounded string lists or
the bounded ordered map entry shape documented in
[map library 0.3.0](wavelengthscript-maps-v0-3.md).
Equality is exact, including list order, duplicates and Unicode code units;
there is no trimming, coercion, normalisation, regex or expression evaluation.
Map equality compares ordered key/value pairs, not unordered object fields.
An expected error matches any interpreter `CollectionVMError` during execution,
not a particular error category. Inputs may deliberately contain invalid VM
values when testing a runtime error.

The runner validates the whole manifest and compiles all selected library
sources before running any case. Unknown IDs, paths, URLs, malformed expectations
and broken package sources cannot become passing expected-error assertions.
Unexpected host exceptions abort rather than passing an error assertion.

## Resource and authority boundaries

- Suite text: at most 131,072 UTF-16 code units; strict UTF-8 at the CLI.
- Between 1 and 64 cases; names at most 80 code units, without control characters.
- Each case's compact serialized input object: at most 16,384 code units.
- Existing VM limits remain unchanged, including at most 1,024 visited
  instructions per case, 32 registers, 20 list items and 256 code units/string.
  At most 65,536 VM instruction visits are possible across 64 cases.
- Programs come only from the fixed generated library catalogue. The suite
  does not load source paths, URLs, callbacks or shell commands.
- The CLI reads only the explicitly selected suite file and writes its local
  report. It does not modify that file or grant programs new capabilities.
- Reports contain case names, program IDs and outcome categories, not input
  values, returned values, raw runtime exception text or source. Case names
  are user-supplied and visible; do not put private information in them.

The generated artifact is the execution source of truth for both browser and
Node tooling. Run `check:wls-library` first to catch a stale artifact; testing a
packaged program does not automatically read newer on-disk `.wls` sources.
This tool remains a normal Node/TypeScript bootstrap, not an OS sandbox or
proof of privacy, application parity or production readiness.

The pure, synchronous `runCollectionTestSuite(text)` function is also exported
from `shared/wls-test-runner.ts` for browser/Node developer integrations without
filesystem or network access. Adding a browser UI is separate work.

## Verification

Focused regressions are in `server/wls-test-runner.test.ts` and
`scripts/wls-collections-cli.test.ts`, including real CLI subprocesses,
pass/fail exit codes, all-before-execution validation, invalid fixtures, exact
comparisons, runtime bounds and unexpected host-error handling.
